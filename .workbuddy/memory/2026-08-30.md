## ESP32-S3 + NestJS 语音链路：TTS 回复时 WebSocket 断连（socket_close）排查

- 现象：正式环境（域名 + Nginx 反代 → 内网端口）TTS 回复播到第二句附近，后端打印
  `[voice] cancel turn turnId=N reason=socket_close`。4 轮样本中 1/2/4 断，第 3 轮（短回答 16 字）正常完成。
- 关键结论：**后端不是主动关闭方**。服务端唯一 close 入口 `voice-session.gateway.ts:276`
  `entry.socket.close()`，只由「空闲 120s 超时」和「新连接顶旧连接」两处触发，两者都会打日志，
  而现场日志里都没有 → close 来自设备端或 Nginx。
- 服务端 `sendBinary`（`voice-session.gateway.ts:242-248`）无 `bufferedAmount` 检查、无 send callback；
  网关完全没有 ping/pong 心跳。
- 设备端缓冲：解码队列 96 帧 × 60ms ≈ 5.76s（`device_voice_client.h:117`）
  + 播放队列 5s（`pcm_playback_queue.h:27`）= 约 10.7s。
  服务端 TTS rtf 0.23~0.45，即 2.2~4 倍实时速度下发，长回答必然打满缓冲。
- 固件背压设计（`device_voice_client.cc:414-439` 注释）依赖「WS 接收任务停读 → TCP 窗口收窄 →
  服务器节流」，但中间插入 Nginx 后该背压被代理缓冲吸收，传不回服务端。
- 设备端另一条自断路径：`device_voice_client.cc:370-380`，只要 `DecodeBinaryFrame`
  返回非 kOk（如 kNotEnough=1）就 `HandleSocketDisconnected(..., "bad_frame")` 主动断连；
  固件未做 WS 分片重组。
- 给出的排查路径（成本从低到高）：① 服务端 close 事件补打 code/reason；
  ② sendBinary 记录 socket.bufferedAmount；③ Nginx location 补
  proxy_read_timeout/send_timeout 3600s + proxy_buffering off + tcp_nodelay on；
  ④ 取设备端 DeviceLog / 串口（看 reason 是 bad_frame 还是复位）；⑤ 内网直连绕开 Nginx 做二分。
## 已实施加固（后端已改完并通过测试，待正式环境验证）

后端 `voice-session.gateway.ts`：
- close 事件补打 `code` + reason（判据：1006=传输层中断 / 1000=设备正常close / 1002·1007=协议错）；error 事件打日志。
- 新增心跳：`VOICE_HEARTBEAT_INTERVAL_MS`（默认 20s）+ `VOICE_HEARTBEAT_MAX_MISSED`（默认 2）。
  心跳**不刷新** lastActiveAt，保持原 120s 空闲关闭语义不变。
- `sendBinary` 增加：send callback 捕获异步错误 + try/catch 吞同步异常（否则会顺着 pacing 定时器
  回调冒泡成未捕获异常打挂 pm2 进程）+ bufferedAmount 观测（超 1MB 每 5s 告警）+ 记录 peakBacklog，
  连接回收时打印。返回 `boolean | void`，false 表示不可写。
- 新增 `VoiceClientEntry` 类型统一 entry 结构。

后端 `voice-turn.service.ts`（核心修复：下行 pacing）：
- 新增输出泵：`enqueueOutputFrame` / `pumpAudioOutput` / `clearOutputPump` / `flushPendingFinale`。
  `sendOpusPacket`、`sendOutputPcm` 由"立即发"改为"入队按音频时长排程发"，下行速率压回 1 倍实时。
- 计划发送时刻 = `audioFirstFrameAt + audioPumpedMs - pacingBudget`；budget 默认 1500ms，
  60s 后放宽到 8s，75s 后 600s（≈全速）—— 防止拖过设备侧 120s 看门狗
  （`headless_voice_controller.cc:45/649`）。
- `completeTurn` 拆分：opusFramer.flush 只入队，`asr.final`/`turn.done` 改为挂在 `pendingFinale`，
  等音频排空后由 `sendTurnFinale` 发送（设备收到 turn.done 即进入等待排空，早发会截断尾音）。
  `persistTurnMessages` 仍在 completeTurn 里同步做，不延后落库。
- 新增 timeline 事件 `turn.finale`；`turn.complete` 增加 `audioMs` / `pendingFrames`。
- `cancelTurnInternal` 调 `clearOutputPump` 清定时器与残余帧。
- 开关：`VOICE_TTS_PACING_ENABLED=false` 可一键退回"拿到就发"。默认开启。
- 帧时长：opus 固定 60ms/帧；PCM 按 `payload.length / 48` 计算（24kHz·16bit·mono）。

固件 `device_voice_client.cc`：
- `bad_frame` 分支补 DeviceLog 诊断（rc 文字含义 + 帧长度 + 头部前 8 字节 hex），零行为变更，
  目的：不接串口也能在网页日志里区分 `not_enough`（WS 分片未重组）与 `bad_magic`（帧错位）。

- **未做** WS 分片重组：本地缺 managed_components，拿不到 `web_socket.h`，无法确认 OnData 的
  分片语义，盲改有把多个独立帧拼接而损坏数据的风险。待用户拉取依赖后确认再改。

新增文件：`backend/deploy/nginx-voice-websocket.conf`（可直接 include 的 location 片段）。

## 首次上线验证 + 第二轮根因（pacing 曾有的预算放宽是新元凶）

turn 1（17:03，7 句 / 366 帧 / 21960ms 音频）：**完全成功**，无断连，pacing 行为与预期一致
（first_audio → turn.finale 间隔 20421ms ≈ 音频 21960ms − 1.5s 预算）。

turn 2（17:08，31 句 / 526 字 / 104s 音频）：**断连 code=1006**，说到一半停。
根因定位（关键数据）：
- `turn.finale audioMs=52980 framesSent=1739` —— 1739×60ms 应为 104340ms，
  但 audioPumpedMs 只有 52980ms ⇒ 入队 1739 帧、实际只发出 883 帧，
  剩下 856 帧在连接断后被 `writable === false` 分支丢弃。
- 领先量 = 52980 − (61541−16614) = 8053ms ≈ `PACING_RELAX_BUDGET_MS`(8000)
  ⇒ turn.startedAt + 60s 时 budget 由 1500 突放宽到 8000，制造了约 6.5 秒的
  **流量突发**，1.5 秒后设备以 code=1006 崩掉。
- `pongMissed=0 / peakBacklog=0`：服务端侧一切正常，是设备被突发冲垮，不是超时也不是积压。

**教训：放宽 pacing 预算 = 把积压风险一次性砸给设备，绝不能做。**
原本担心的"pacing 拖过设备 120s 看门狗"不该用加速解决，应该用截断。

修复（已改，voice 模块 86 用例通过）：
- 删除 `PACING_RELAX_AFTER_MS/RELAX_BUDGET/ESCALATE_*`，budget 恒定 1500ms。
- 新增 `VOICE_TTS_MAX_AUDIO_MS`（默认 90000，readEnvNumber 限 10s~300s）：
  VoiceTurn 增加 `audioQueuedMs`（入队即累加），consumer 每句合成前判定，
  超限则停止后续合成并打 `tts.audio_cap` timeline —— 宁可截断，不制造突发。
- pump 中 `writable === false` 改为**丢弃 pendingFinale** 而非 flush，
  避免打印 `turn.finale status=done` 掩盖"其实断在半路"（原来那条日志是误导）。
- `turn.complete` 日志补 `audioQueuedMs`，与 `audioPumpedMs` 分开，便于对账。
- 新增用例：单轮音频上限截断验证（上限 2000ms / 每句 1000ms → 只合成 2 句 = 20 块）。

## 设备端日志验证（第三轮）：pacing 已确认生效，H2 排除

设备端网页日志（同一时段）给出的决定性证据：

**turn 1 完全成功，且是 pacing 有效性的最强证明：**
- `ws 音频排空: turn=1 frames=366` —— 与后端 `ttsFramesSent=366` **精确对账，零丢帧**。
- `本轮播完 samples=527040(约21960ms) 断档=0次` —— 与后端 `audioMs=21960` 完全一致；
  **断档 0 次** 说明播放队列全程未被掏空，1 倍实时 pacing 的平滑性得到验证。

**17:06:25 `ws 已断开: generation=2 reason=server_closed` 属正常行为**：
距 17:04:19 播完约 126s ≈ 服务端 `VOICE_IDLE_CLOSE_MS`(120s) + 10s 检查周期。
设备按设计回到 Ready，17:08:53 按 PTT 立即重连成功。非故障。

**turn 2（17:09:55）设备侧 reason 也是 `server_closed`，不是 `bad_frame`**
⇒ 设备**没有**走 `DecodeBinaryFrame` 失败的自断路径，**H2（WS 分片未重组）排除**。
且日志中 17:09:55 之后没有 `AiClient登录成功 / WiFi 已连接 / NTP 校时` 等启动序列
⇒ **设备没有复位**，是 WebSocket 连接被 abort，而非芯片崩溃。
- turn 2 缺少 `ws 音频排空` 与 `本轮播完` ⇒ 设备从未收到 turn.done
  （后端那条 turn.finale 是 `writable===false` 分支的伪完成，turn.done 实际未发出）。

后续改动：
- 固件：把 `OnDisconnected` 的 reason 由 `server_closed` 改为 `transport_closed`。
  该回调与断连发起方无关（服务端关/反代超时/本地 TCP 出错/接收缓冲异常都走这里），
  原名会误导排查方向。仅影响日志字符串，无逻辑依赖。
- 后端：`DEFAULT_MAX_TURN_AUDIO_MS` 由 90000 下调为 **60000**。原值在"录音>15s"时就会
  撞设备 120s 看门狗（30s 录音 + 15s chat 首字 + 90s 音频 = 135s）。
  60s 时最坏 30+15+60=105s，留有余量。

## 第四轮：turn 3 服务端已完全成功，"断"的是内容不是连接

turn 3（17:33，506 字 / 30 句分句 / 实际合成 19 句）：
```
+29850ms  tts.audio_cap audioQueuedMs=60000 limit=60000   ← 60s 上限截断
+65839ms  turn.finale status=done audioMs=60000 framesSent=1000
+65839ms  turn.complete ... audioQueuedMs=60000 audioPumpedMs=60000 pendingFrames=0
```
**服务端全程成功，没有任何 code=1006 / cancel turn / socket_close。**
- `audioQueuedMs == audioPumpedMs == 60000`、`pendingFrames=0` ⇒ 1000 帧全部发出、零丢弃。
- first_audio(+7380) → turn.finale(+65839) 间隔 58459ms ≈ 60000 − 1500(LEAD) ⇒ **pacing 精确成立**。
- turn 总时长 65.8s，距设备 120s 看门狗还有 54s 余量。
- 30 句分句只合成到 19 句 ⇒ 用户听到的"说到一半停"是**内容截断**，不是连接断。

**认识到固定上限的缺陷**：60s 是拍脑袋的安全值，本次明明还有 54s 余量却提前截断了。

改为动态预算（已实现，88 用例通过）：
- 常量：`DEVICE_TURN_DEADLINE_MS=120000`（设备 kTurnDeadlineMs）、
  `TURN_DEADLINE_SAFETY_MS=15000`；`DEFAULT_MAX_TURN_AUDIO_MS` 由 60000 上调为 **120000**
  （改为"产品向硬上限"，安全由动态预算负责）。
- 新增 `turnAudioBudgetMs(turn)`：
  `min(硬上限, 120000 + LEAD − 首帧相对 turn.startedAt 的偏移 − 15000)`。
  推导：turn.done 预计时刻 ≈ 首帧时刻 + audioQueuedMs − LEAD，必须早于
  turn.startedAt + 120000。故 **Chat 越慢（首帧越晚）可说的音频越短**，自动收紧。
- 本次场景（首帧偏移 7380ms）：预算 = 120000+1500−7380−15000 = **99120ms**，
  比原来的 60000ms 多说约 39 秒，506 字基本能讲完。
- `tts.audio_cap` 日志新增 `cappedBy=hard_limit|device_deadline`，便于分辨是产品限制还是安全兜底。
- 新增 2 条用例直接验证预算数学（首帧 2s→104500、40s→66500、120s→0、硬上限 30000 生效）。

## 第五轮：实现 turn.progress 心跳续期（用户选定方案）

动机：单纯调大设备 `kTurnDeadlineMs` 会把故障恢复时间从 2 分钟拉到 3 分钟；
改为"后端下发期间发心跳、设备收到即续期"，可同时做到超长回复不撞线 +
故障检测从 120s 缩到 20s。

**协议**：新增 `turn.progress`（仅带 turnId）。老固件不认识该 type，
`ParseServerMessage` 返回 false 后被 HandleText 直接忽略 ⇒ 双向兼容。

**后端 voice-protocol.ts**：新增 `TurnProgressMessage`，加入 `ServerVoiceMessage` 联合类型。

**后端 voice-turn.service.ts**：
- 常量 `DEFAULT_DEVICE_TURN_DEADLINE_MS=120000`（原硬编码改为可配）、
  `DEFAULT_TURN_PROGRESS_INTERVAL_MS=5000`、`TURN_DEADLINE_SAFETY_MS=15000`（不变）。
- 新增 env：`VOICE_DEVICE_TURN_DEADLINE_MS`(30s~600s)、`VOICE_TURN_PROGRESS_INTERVAL_MS`(1s~30s)；
  `VOICE_TTS_MAX_AUDIO_MS` 上限放宽到 600s。
- VoiceTurn 新增 `finaleSent`、`progressTimer`；新增 `startTurnProgress` / `stopTurnProgress`。
- 首帧发出即起搏并立即发一次；`clearOutputPump`（取消路径）与 `flushPendingFinale`
  （收尾路径）都停心跳。顺序：stop → finaleSent=true → sendTurnFinale，
  保证 turn.done 之前心跳已停（否则设备排空阶段被续期，掩盖真卡死）。
- 动态预算改用 `this.deviceTurnDeadlineMs`（不再引用已删除的 DEVICE_TURN_DEADLINE_MS 常量）。

**固件 voice_protocol.h/.cc**：MessageType 加 `kTurnProgress`；ClassifyMessage 加
`"turn.progress"` 分支（放在最后，不影响既有type）。

**固件 headless_voice_controller.cc**：
- 新增 `kTurnProgressTimeoutMs = 20000`（容许连丢 3 次心跳）。
- OnEvent 新增 case：**严格匹配 `msg.has_turn_id && msg.turn_id == current_turn_id_`**
  才续期 —— 旧轮迟到的心跳给新轮续期会导致新轮卡死永远检测不到。
- 超时日志去掉硬编码 "(120s)"：等待中可能是初始 120s 也可能是心跳 20s，写死会误导。

**要真正支持超长回复需同时满足（缺一不可）**：
1. 烧录含 turn.progress 续期的固件；
2. `VOICE_DEVICE_TURN_DEADLINE_MS` 调大（后端据此算预算）；
3. `VOICE_TTS_MAX_AUDIO_MS` 调大（否则被产品硬上限卡住）。
例：想要 300s 音频 → 两者分别 ≥ 约 320000 与 300000。

验证：类型检查 OK，voice 模块 **89 用例通过**（新增 1 条心跳测试：
首帧即有心跳、均带 turnId、turn.done 之后不再增长）。
