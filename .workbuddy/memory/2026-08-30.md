## ESP32-S3 + NestJS 语音链路：TTS 回复时 WebSocket 断连（socket_close）排查

- 现象：正式环境（域名 + Nginx 反代 → 内网端口）TTS 回复播到第二句附近，后端打印
  `[voice] cancel turn turnId=N reason=socket_close`。4 轮样本中 1/2/4 断，第 3 轮（短回答 16 字）正常完成。
- 关键结论：**后端不是主动关闭方**。服务端唯一 close 入口 `voice-session.gateway.ts:276`
  `entry.socket.close()`，只由「空闲 120s 超时」和「新连接顶旧连接」两处触发，两者都会打日志，
  而现场日志里都没有 → close 来自设备端或 Nginx。
- 服务端 `sendBinary`（`voice-session.gateway.ts:242-248`）无 `bufferedAmount` 检查、无 send callback；
  网关完全没有 ping/pong 心跳。
- 设备端缓冲：解码队列 96 帧 × 60ms ≈ 5.76s（`device_voice_client.h:117`）
  + 播放队列 5s（`pcm_playback_queue.h:27`）= 约 10.7s。
  服务端 TTS rtf 0.23~0.45，即 2.2~4 倍实时速度下发，长回答必然打满缓冲。
- 固件背压设计（`device_voice_client.cc:414-439` 注释）依赖「WS 接收任务停读 → TCP 窗口收窄 →
  服务器节流」，但中间插入 Nginx 后该背压被代理缓冲吸收，传不回服务端。
- 设备端另一条自断路径：`device_voice_client.cc:370-380`，只要 `DecodeBinaryFrame`
  返回非 kOk（如 kNotEnough=1）就 `HandleSocketDisconnected(..., "bad_frame")` 主动断连；
  固件未做 WS 分片重组。
- 给出的排查路径（成本从低到高）：① 服务端 close 事件补打 code/reason；
  ② sendBinary 记录 socket.bufferedAmount；③ Nginx location 补
  proxy_read_timeout/send_timeout 3600s + proxy_buffering off + tcp_nodelay on；
  ④ 取设备端 DeviceLog / 串口（看 reason 是 bad_frame 还是复位）；⑤ 内网直连绕开 Nginx 做二分。

## 首次上线验证 + 第二轮根因（pacing 曾有的预算放宽是新元凶）

turn 1（17:03，7 句 / 366 帧 / 21960ms 音频）：**完全成功**，无断连，pacing 行为与预期一致
（first_audio → turn.finale 间隔 20421ms ≈ 音频 21960ms − 1.5s 预算）。

turn 2（17:08，31 句 / 526 字 / 104s 音频）：**断连 code=1006**，说到一半停。
根因定位（关键数据）：
- `turn.finale audioMs=52980 framesSent=1739` —— 1739×60ms 应为 104340ms，
  但 audioPumpedMs 只有 52980ms ⇒ 入队 1739 帧、实际只发出 883 帧，
  剩下 856 帧在连接断后被 `writable === false` 分支丢弃。
- 领先量 = 52980 − (61541−16614) = 8053ms ≈ `PACING_RELAX_BUDGET_MS`(8000)
  ⇒ turn.startedAt + 60s 时 budget 由 1500 突放宽到 8000，制造了约 6.5 秒的
  **流量突发**，1.5 秒后设备以 code=1006 崩掉。
- `pongMissed=0 / peakBacklog=0`：服务端侧一切正常，是设备被突发冲垮，不是超时也不是积压。

**教训：放宽 pacing 预算 = 把积压风险一次性砸给设备，绝不能做。**
原本担心的"pacing 拖过设备 120s 看门狗"不该用加速解决，应该用截断。

修复（已改，voice 模块 86 用例通过）：
- 删除 `PACING_RELAX_AFTER_MS/RELAX_BUDGET/ESCALATE_*`，budget 恒定 1500ms。
- 新增 `VOICE_TTS_MAX_AUDIO_MS`（默认 90000，readEnvNumber 限 10s~300s）：
  VoiceTurn 增加 `audioQueuedMs`（入队即累加），consumer 每句合成前判定，
  超限则停止后续合成并打 `tts.audio_cap` timeline —— 宁可截断，不制造突发。
- pump 中 `writable === false` 改为**丢弃 pendingFinale** 而非 flush，
  避免打印 `turn.finale status=done` 掩盖"其实断在半路"（原来那条日志是误导）。
- `turn.complete` 日志补 `audioQueuedMs`，与 `audioPumpedMs` 分开，便于对账。
- 新增用例：单轮音频上限截断验证（上限 2000ms / 每句 1000ms → 只合成 2 句 = 20 块）。

  **断档 0 次** 说明播放队列全程未被掏空，1 倍实时 pacing 的平滑性得到验证。

**17:06:25 `ws 已断开: generation=2 reason=server_closed` 属正常行为**：

设备按设计回到 Ready，17:08:53 按 PTT 立即重连成功。非故障。

**turn 2（17:09:55）设备侧 reason 也是 `server_closed`，不是 `bad_frame`**
⇒ 设备**没有**走 `DecodeBinaryFrame` 失败的自断路径，**H2（WS 分片未重组）排除**。

## 第四轮：turn 3 服务端已完全成功，"断"的是内容不是连接

turn 3（17:33，506 字 / 30 句分句 / 实际合成 19 句）：
```
+29850ms  tts.audio_cap audioQueuedMs=60000 limit=60000   ← 60s 上限截断
+65839ms  turn.finale status=done audioMs=60000 framesSent=1000
+65839ms  turn.complete ... audioQueuedMs=60000 audioPumpedMs=60000 pendingFrames=0
```
**服务端全程成功，没有任何 code=1006 / cancel turn / socket_close。**
- `audioQueuedMs == audioPumpedMs == 60000`、`pendingFrames=0` ⇒ 1000 帧全部发出、零丢弃。
- first_audio(+7380) → turn.finale(+65839) 间隔 58459ms ≈ 60000 − 1500(LEAD) ⇒ **pacing 精确成立**。
- turn 总时长 65.8s，距设备 120s 看门狗还有 54s 余量。
- 30 句分句只合成到 19 句 ⇒ 用户听到的"说到一半停"是**内容截断**，不是连接断。

**认识到固定上限的缺陷**：60s 是拍脑袋的安全值，本次明明还有 54s 余量却提前截断了。

改为动态预算（已实现，88 用例通过）：
- 常量：`DEVICE_TURN_DEADLINE_MS=120000`（设备 kTurnDeadlineMs）、
  `TURN_DEADLINE_SAFETY_MS=15000`；`DEFAULT_MAX_TURN_AUDIO_MS` 由 60000 上调为 **120000**
  （改为"产品向硬上限"，安全由动态预算负责）。
- 新增 `turnAudioBudgetMs(turn)`：
  `min(硬上限, 120000 + LEAD − 首帧相对 turn.startedAt 的偏移 − 15000)`。
  推导：turn.done 预计时刻 ≈ 首帧时刻 + audioQueuedMs − LEAD，必须早于
  turn.startedAt + 120000。故 **Chat 越慢（首帧越晚）可说的音频越短**，自动收紧。
- 本次场景（首帧偏移 7380ms）：预算 = 120000+1500−7380−15000 = **99120ms**，
  比原来的 60000ms 多说约 39 秒，506 字基本能讲完。
- `tts.audio_cap` 日志新增 `cappedBy=hard_limit|device_deadline`，便于分辨是产品限制还是安全兜底。
- 新增 2 条用例直接验证预算数学（首帧 2s→104500、40s→66500、120s→0、硬上限 30000 生效）。

### 二次更正：prefill 差异与 history 无关，7288ms 是异常值

重新核对原始日志，**我此前写的 "history=4 vs 2" 是记错了**：
- turn 2（1:57）实际 `history=1 → 2`（restart 前后），prefill 7288ms
- turn 3（3:06）`history=1`，prefill 3795ms
- turn 3'（17:33）prefill 3755ms

即 history=1 与 history=2 的两次分别为 3795 / 7288ms，而第三次又是 3755ms
⇒ **turn 2 的 7288ms 是模型服务当时的负载波动（离群值），不是 history 造成的**。
**基线 prefill ≈ 3.75s。** 因此"砍 history 省 3.5 秒"的建议**不成立，已撤回**。

### history 的真实含义（代码事实）

`voice-turn.service.ts:1551 buildHistory()` → `messagesService.findRecentByConversation(
userId, conversationId, 20)`（`messages.service.ts:227`，`orderBy createdAt desc, take: limit`
再 `reverse()`）。
- 取的是**最近 20 条 message**（不是 20 轮；一轮 = user+assistant 两条）。
- 日志里的 `history=N` 是最终 messages 数组的**条目数**（= recent + 当前这条）。
- 无 conversationId 时退化为仅当前一条（新会话必然 history=1）。
- **"砍 history"= 调小这个 limit，数据库不删任何记录**，APP 端历史仍完整。
- 实测当前只有 1~4 条，离 20 上限很远 ⇒ 现阶段砍它无收益。

### prefill 的真实大头（固定不变的部分）

每次请求都相同的：system prompt + `memories=14` 条长期记忆 + `tools=12` 个工具的 JSON Schema
（`src/shared/ai/chat-tools.ts` 共 1021 行）。这部分才是 ~3.75s 的主要来源，
也正是 MiMo 自动前缀缓存（cached_tokens）的理想对象。

## 前缀缓存排查结论（关键发现：当前几乎完全失效）

**语音路径实际注册 12 个工具**（`buildVoiceTools` voice-turn.service.ts:1654，
注释说明刻意不含 generateImage/generateDocument，因语音设备无屏）：
- 搜索：webSearch
- 日程/提醒：createSchedule、updateSchedule、cancelSchedule、completeSchedule、queryPlans（5 个）
- 待办：createTodo
- 备忘：createMemo、queryMemos
- 记账：recordExpense、recordIncome、queryAccounting（3 个）
（chat-tools.ts 共定义 14 个，减 2 个 = 12，与日志 `tools=12` 吻合。）

**system prompt 拼装顺序**（chat-ai.service.ts:346-531 `buildSystemPrompt`，数组末尾）：
```
[固定角色设定 + 语音输出指令] → [12 个工具的调用指令] → Current time context
 → User location → Conversation title → Durable memory
 → Structured records → Retrieved historical context
```

**根因：`Current time context` 精确到毫秒**（`shared/time/ai-current-time.ts:38`
`utcNow=${now.toISOString()}`、`localTime` 含 `second`）⇒ 每次请求该处必变，
其后所有内容（memories / records / retrieved context **以及 messages 数组里的 history**）
全部无法命中前缀缓存。注意 history 是追加式的、本身前缀稳定，
但因排在会变的 system prompt 之后而白白失去缓存。

**次因：memories 排序不稳定**（memories.service.ts:276-305）：
`orderBy {updatedAt:'desc'}` 取 300 条后，再按 `type 优先级 → updatedAt desc` 排序。
任何记忆被更新都会改变注入顺序。

**建议改法（按性价比）**：
A. 把 `Current time context` 移到 system prompt **最后**（records/retrieved 之后）——
   零成本，能让「角色设定+工具指令+memories」整段稳定可缓存，且 history 得以保留前缀。
   风险：指令位置变化可能影响模型对时间的关注，需实测。
B. 时间精度降到分钟（去毫秒/秒）—— 风险低但收益也低（对话间隔常 >1 分钟）。
C. memories 次排序改 `id` 而非 `updatedAt` —— 稳定，但"最近更新的记忆靠前"语义会丢。
D. 精简工具（5 个日程工具可合并）—— 收益最直接但要重调 prompt，风险最高。
**建议先加 `usage.prompt_tokens_details.cached_tokens` 日志用真实数据验证再动。**

## MiMo Chat API 文档要点（https://mimo.mi.com/docs/zh-CN/api/chat/openai-api）

- **有自动前缀缓存**：响应里 `usage.prompt_tokens_details.cached_tokens`（"命中缓存的 token 数量"）
  证明后端确实有缓存，但**没有暴露任何控制参数**（无 cache_control / prompt_cache_key）。
  ⇒ 想提高命中率只能靠**保持 prompt 公共前缀稳定**：system + memories + tools 顺序固定且靠前，
  把会变的 history 放后面。
- **`thinking` 默认 enabled**（mimo-v2.5 / v2.5-pro 都是）→ 本项目已传 `thinking:{type:"disabled"}`，
  日志 `thinkingEnabled=false` 确认生效。✓ 这点没得优化了。
- **`max_completion_tokens`**：mimo-v2.5 默认 32768、v2.5-pro 默认 131072。
  **这是控制回复长度的官方手段**，可直接限制超长回复（比在 audio 层截断更合理）。
- **tools**：支持 function；另有内建 `web_search` tool（本项目用的是自己的 volcengine SearchService，
  日志 `SearchService Searching with provider: volcengine`，未走 Mimo 内建搜索）。
- **stream**：支持 SSE ✓。**stop**：最多 4 个序列，可当截断兜底。
- 无 service_tier / 无 TTFT 专项参数。模型可选 `mimo-v2.5-pro`（更大更慢）、`mimo-v2.5`（当前在用）。

## 延迟分析（用户问"松手→出声能否加快"，仅分析未改）

**松手 → 出声** 实测分解：
| 轮次 | ASR+调度 | Chat 首字 | TTS 首帧 | 合计 |
|---|---|---|---|---|
| turn 3（17:33，Chat 松手后才启动） | 465ms | 3755ms | 600ms | **4820ms** |
| turn 2（1:57，Chat 录音中已预热） | —（提前跑掉） | 3028ms | 720ms | **3748ms** |

- Chat 首字是绝对大头，占 turn 3 松手后耗时的 78%。
- **turn 2 更快不是因为模型更快**：它 `elapsedFromChatRequest=7288ms` 反而比 turn 3 的
  3755ms 慢一倍，但 Chat 在用户还说着的时候就跑了 4.7 秒（路线 B 预热），把延迟吃掉了。
  ⇒ **最大杠杆是让 Chat 更早启动**，而不是优化模型。
- 首字延迟 vs history 疑似正相关：turn 2(history=4)=7288ms、turn 4(history=3)=3795ms、
  turn 3=3755ms。样本仅 3 个且跨时段，**不足以定论**。
- 其余项空间很小：ASR 已预热（465ms）；TTS 首帧 600ms 中 TTS 本身只占 133ms
  （`firstAudio=133ms`），剩下是本地分句/请求开销。

**待修回归（我自己引入的，尚未修）**：
